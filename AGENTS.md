# AGENTS.md

These rules are mandatory for every human or agent modifying Nodex. Prefer executable enforcement when a rule can be verified objectively. When a requested change conflicts with this contract, redesign the implementation rather than violating it.

## Architecture and dependencies

Every first-level package under `internal/` is a bounded root representing an architectural capability or territory.

Cross-root dependencies are always root-to-root: `internal/foo` may import `internal/bar`, but never `internal/bar/contracts`, `internal/bar/types`, `internal/bar/schema`, `internal/bar/parser`, or any other subpackage of `bar`. Subpackages are private implementation details. Names such as `contracts`, `schema`, `types`, `driver`, `postgres`, and `oauth` receive no exemption. Packages within one root may depend on that root's subpackages, forming an internal DAG.

A root package is a semantic facade, not a barrel package. Expose only stable concepts and capabilities that genuinely belong to its API. Do not bypass boundaries through aliases, bulk re-exports, generic containers, or dependency indirection.

Dependencies between bounded roots must form a DAG. Solve reverse requirements through consumer-owned ports and composition. The consuming root defines the interface when it needs a capability without depending on another territory's implementation; composition supplies the implementation. Do not move interfaces to providers merely to invert dependencies.

`cmd/...` constructs implementations and adapters and connects bounded roots. Composition must not contain product or domain logic.

Neutral foundations are explicit exceptions with a clear, reusable, self-contained responsibility. They may own neutral primitives and mechanisms, but never product rules. Do not create generic `utils`, `helpers`, `common`, or `shared` escape packages. Code and types belonging to a territory remain there; do not create generic `model`, `types`, or `schema` roots merely because several packages need data structures.

Prefer simple structures over speculative abstractions. Do not create packages, interfaces, foundations, or extension mechanisms for hypothetical future needs. A subpackage must represent a coherent responsibility, not an individual file or tiny concept; a couple of helpers generally belong in the existing package.

## Package, documentation, and test conventions

Under `internal/`, allow only `internal/<root>` and `internal/<root>/<subpackage>`; deeper package trees are forbidden.

Packages with multiple files keep a conceptual root file matching the package name as their main reading entry point, such as `internal/index/index.go`. General package documentation belongs there. Every exported symbol carries GoDoc next to its declaration; do not centralize documentation for symbols declared elsewhere.

Internal comments should add information not evident from the code. GoDoc and code comments must describe the current contract, invariants, limits, and behavior without requiring knowledge of prompts, reports, development phases, ADRs, roadmaps, migrations, tickets, or implementation history. Do not narrate history. References to external technical standards may add precision, but explain the relevant semantics locally.

Under `internal/`, packages with tests keep exactly one canonical `<package>_test.go`, named after the package directory. Elsewhere, prefer one canonical `<package>_test.go` per package and split tests only for a real reason.

`tests/architecture` must inspect packages and imports and reject objective violations, including cross-root subpackage imports, forbidden generic packages, excessive depth, invalid root dependencies, root cycles, and noncanonical internal test-file layouts. Important checks must include controlled artificial violations proving their failure paths. Enforce objective rules mechanically; do not replace semantic rules with weak string-matching heuristics. Semantic quality remains a review concern when no reliable mechanical check exists. Validate changes with `go test ./...`, `go vet ./...`, and `go test ./tests/architecture`.

## Repository conventions are not product assumptions

Development directories, paths, naming conventions, tools, workflows, architecture rules, and other repository-specific artifacts do not automatically become special behavior in repositories analyzed by Nodex. Including, excluding, or otherwise treating a path specially requires an independent product decision. New development conventions must not silently acquire product meaning.

## Product boundaries and ownership

Nodex is a multilingual source-code indexing tool; Go is the first supported language. Nodex collects, indexes, localizes, manages snapshots, and retrieves source comments and declarations. A documentation relationship is a parser-derived structural fact: the declaration either has a directly associated documentation comment or it does not. That absence is not a quality judgment. Nodex must not judge comment meaning or quality, rewrite comments, call an LLM, classify comments as good or bad, decide that a declaration requires documentation, or become an intelligent linter. Semantic analysis belongs outside Nodex.

Five bounded roots own the work:

- `internal/project` resolves the source root and independent workspace base, discovers regular files inside that filesystem boundary, and reads the exact bytes of a canonical logical path within it.
- `internal/ignore` compiles and matches manual exclusions and stores enabled concrete preset identifiers and ordered manual patterns. It takes configuration bytes from the caller and does not open the document, discover files, or interpret preset semantics.
- `internal/syntax` interprets caller-supplied source into language-neutral documents, comments, and declarations and owns supported languages and language-aware presets. It returns bounded structural context around a comment range or a declaration range as a physical source slice carrying no syntax tree. Documentation association is the parser's direct relationship. It does not walk the filesystem or read ignore configuration.
- `internal/index` orders comments and declarations, assigns snapshot-local comment IDs and declaration IDs, persists the index, and owns currentness comparison. A declaration stores the ID of its directly associated comment when the ranges match exactly, and stores no comment text. It does not discover files, match exclusions, or parse source.
- `internal/skill` embeds one canonical provider-neutral Agent Skill and installs or removes that same document at a caller-supplied base. Targets select project-relative or home-relative destinations without changing the text. The package does not resolve project roots or homes, read source, parse comments, match exclusions, or persist Nodex state.

`cmd/nodex` composes these roots. Nodex distributes the embedded skill to describe the public command workflow to an external agent; it does not execute the skill.

## Language architecture

`internal/syntax` is the language-neutral semantic facade consumed by other bounded roots. `internal/syntax/contracts` owns the private contract for a complete language implementation, including contractual inputs, outputs, and invariants. `internal/syntax/types` contains only structural vocabulary genuinely shared inside the syntax root. Neither private package is an external API; consumers outside syntax import only `internal/syntax`, never any syntax subpackage.

Each `internal/syntax/<language>` implementation completely owns its language-specific recognition, parsing, comment normalization, declarations, direct documentation relationships, structural context, preset catalog, aggregate selectors, and exclusion semantics. Go is implemented in `internal/syntax/golang`, and Go syntax trees stay there. Each language exposes one `New()` capability object satisfying `contracts.Language`, with compile-time enforcement. The syntax root owns one explicit static language registry in `internal/syntax/languages.go`; there is no independent preset registry or self-registration. Adding a language requires only creating its private subpackage, implementing the contract, importing it in that registry, and registering its `New()` result. The facade resolves a unique implementation, invokes its capability, and adapts neutral values; it contains no language-specific dispatch outside composition. Duplicate identities or selectors and overlapping path recognition violate registry invariants.

Language recognition uses case-sensitive path suffixes without inspecting contents; Go currently recognizes `.go`. Parsing returns every language-defined comment unit in physical order, with its exact raw bytes and normalized text that preserves directives, and the declaration facts from that same parse. Positions use zero-based byte offsets, one-based lines and byte columns, and half-open ranges; source line directives must not relocate them. Unsupported paths or malformed source return an error without a partial document. Go parsing does not type-check, resolve imports, or select files by build constraints.

For Go, the indexed declarations are the package clause, functions, methods, parenthesized const, var, and type groups, each const or var value spec, each type spec, and struct or interface fields. Imports are not declarations in this index. A declaration's documentation comment is only the comment the parser attached directly to that node. A group comment is not copied onto a child, and a child comment is not copied onto the group. A node with no direct documentation comment is still a declaration.

Context identifies a comment or a declaration by its exact physical range, never its text. Bounds belong to `syntax`; snippets are contiguous original source bytes without reformatting or inserted ellipses. A declaration snippet keeps the start of the declaration when the rest of the body exceeds the context limit.

The language registry derives supported preset catalogs and aggregate expansions from those same language objects. `internal/syntax/languages.go` owns registry state, derived catalogs, invariants, selector expansion, and exclusion dispatch; `internal/syntax/syntax.go` exposes the public semantic operations; each language owns preset semantics in its implementation package's `presets.go`. Syntax collects globally unique identifiers, expands language-provided aggregates, and dispatches enabled preset evaluation to the recognized language. Current Go presets are `go:tests`, `go:vendor`, and `go:generated`, defined in `internal/syntax/golang/presets.go`. `go:all` expands to those concrete identifiers and is not a preset. `go:tests` matches Go basenames ending in `_test.go`; `go:vendor` matches Go files beneath a `vendor` path element; `go:generated` uses Go's structural generated-file convention, not a loose text search. Platform-specific names and build-tagged files remain ordinary source unless a manual exclusion or enabled preset removes them.

## Project resolution and control directory

Automatic root resolution starts at the process working directory and walks ancestors to the nearest language-neutral marker. A real `.nodex` directory takes precedence over `.git` in the same directory. `.git` may be a real directory or regular file. Symbolic links named `.nodex` or `.git` are errors and are not followed; any other invalid marker type is also an error. Resolution stops at the marker, does not use language manifests such as `go.mod` or `go.work`, and does not split the tree into several roots. Without a marker, the starting directory is the root.

The global syntax is `nodex [--root <path>] [--out-dir <path>] <command> ...`; both options precede the top-level command. `--root` selects only the source root through `project.Open`, without ancestor discovery. Without it, source discovery starts at the invocation cwd using the marker rules above. `Open` establishes an absolute, cleaned boundary and resolves links in the supplied path to the actual directory.

The workspace base owns the control directory, always `<workspace-base>/.nodex`. Explicit `--out-dir` selects that base. Without `--out-dir`, explicit `--root` uses invocation cwd as the workspace; without either option, the workspace is the resolved source root. Relative option paths are interpreted from captured invocation cwd. Workspace bases must be existing directories, canonicalized with links resolved; selection creates nothing. `internal/project` owns these resolution rules. Source and workspace selection are independent, and the workspace may be outside or inside the source boundary. Control-component link and type checks still apply beneath it. There is no environment-variable override, home-global state, source-root fallback, or persisted absolute location identity.

Discovery returns regular files in lexical order with canonical, slash-separated paths relative to that boundary. It skips symbolic links and other non-regular entries and never traverses directories named `.git` or `.nodex` at any depth; exclusions cannot re-include them. It applies the caller-supplied `project.ExclusionPolicy` port without interpreting policy semantics or reading `.gitignore`. `ReadFile` rejects absolute, escaping, or unclean logical paths, control-directory components, directories, and symbolic links, including intermediate links; it does not repair invalid paths or apply exclusions.

`.nodex/` is Nodex's only control-directory name: persistent workspace configuration and generated state live beneath it. It belongs to the selected workspace base, which need not be the source root. Discovery always excludes it as a product decision independent of ignore patterns. Do not require other root-level control files such as `.nodexignore`, `.nodexrc`, or `nodex.yaml`.

External agents' skill directories are not Nodex control directories. Project-local skill installation uses ordinary root resolution and writes only the agent's destination, without installed-target state under `.nodex/`. Skill commands do not create or modify `.nodex/`. Provider targets differ only by installation path.

Skill operations require an existing base directory and reject symbolic links beneath it. Installation writes the embedded bytes, leaves an identical skill in place, and replaces only a file carrying the Nodex ownership marker. Uninstallation removes only a managed skill and its empty final `nodex` directory; other files and parent directories remain. Unmanaged destinations must never be overwritten or deleted. The installed document comes from the embedded asset; runtime downloads or checkout files must not supply its content.

## Ignore policy

Workspace-specific exclusions belong to persistent `<workspace-base>/.nodex/ignore.json`. Ignore policy and index state always use the same workspace; a source-root ignore document has no effect when another workspace is selected. Schema 1 requires integer `schema: 1`, a `presets` array of concrete preset identifiers, and an `exclude` array of manual patterns. Manual patterns preserve order and duplicates. Preset identifiers form a set: reject duplicates and canonicalize in lexical order. No preset is enabled by default. A missing document means no presets or manual exclusions; reading it must not create it. Manual patterns are project decisions, not built-in repository conventions. Reject unknown fields, invalid UTF-8, null arrays, trailing data, or invalid entries as document errors; never use a partially compiled policy.

Manual matching is exact and ordered: the last matching rule decides, and `!` negates a rule. Patterns use slash-separated elements; a trailing unescaped `/` is directory-only, a leading or internal `/` anchors a pattern at the project root, and a bare name matches at any depth. `**` is recursive only as a whole element. An excluded ancestor seals its subtree, so negation can re-include a file only when its ancestors remain traversable. Do not clean candidate paths, fold case, normalize Unicode, or treat dotfiles specially.

`internal/ignore` stores the policy; `internal/syntax` owns language-aware preset meanings. Aggregate selectors such as `go:all` are command-line expansion tokens for the concrete presets known by the running binary and must never be persisted. Reject documents containing aggregate tokens or unknown identifiers before generation or currentness proceeds. Manual path exclusions apply during discovery.

Ignore reads and writes reject symbolic links at `.nodex` or `ignore.json`. Edits preserve manual patterns and publish a validated document through a temporary file and rename. An edit that leaves policy identity unchanged does not rewrite or create the document.

## Generated index and currentness

`<workspace-base>/.nodex/index/` is disposable derived state. Generation may create it and replace `snapshot.json`, `comments.jsonl`, and `declarations.jsonl`; `snapshot.json` is the commit marker for the set. Publish through temporary files in the index directory, replacing comments first, declarations second, and the snapshot last. The snapshot records the exact digest and count of each derived file; loading rejects inconsistent or malformed state, including mixed generations and a missing derived file. Absence of the snapshot means no committed index. State directories must be real directories, and loading rejects symbolic links in committed paths.

Comment ordering is deterministic by logical path and physical position, never by text or caller input order. Comment IDs start at `C000001`. Declaration ordering is deterministic by logical path, physical start offset, physical end offset, and declaration kind when those ranges are equal. Declaration IDs start at `D000001`. Both sequences use at least six digits and are local to that snapshot, not permanent references across regeneration. Stored comments contain normalized text and physical locations. Stored declarations contain kind, names, physical location, and the comment ID of a directly associated documentation comment when one exists. They do not contain comment text, raw source, syntax trees, or structural context. Do not store absolute paths, timestamps, or machine identity.

A snapshot is current only when its recorded ignore-policy identity and ordered source fingerprints match the effective workspace policy and included supported sources. Source-root and workspace-base identity are not compared or persisted; identical policy and source fingerprints can use a snapshot across source roots. Policy identity covers the canonical preset set and compiled manual rules. Each fingerprint contains the logical path, recognized language, and SHA-256 digest of the exact source bytes. Comment text, declaration facts, documentation relationships, derived-file digests, and file modification times are not part of this comparison. Policy identity hashes the compiled policy, not JSON bytes; formatting, object-field order, and preset ordering do not make a snapshot stale.

Sources excluded by enabled presets are absent from the fingerprint set; changing them does not make a snapshot stale. Changing the enabled preset set changes policy identity and makes an existing snapshot stale. Changes within `.nodex/index/` are never source inputs because discovery excludes `.nodex/`.

Currentness belongs to `internal/index` and must not parse source to rediscover comments or declarations. Source selection may inspect structure when a structural preset is enabled; this is not indexing. Without structural presets, currentness compares only policy identity and byte fingerprints.

## Command behavior

Snapshot operations live under `nodex index`. The previous top-level `generate`, `comments`, `status`, and `show` commands are not commands.

- `index generate` persists the comment and declaration index from one parse of each included supported source.
- `index comments [--file <path> [<path>...]]` emits selected comments from the current index as compact Markdown containing only comment IDs, logical source-root-relative file paths, and normalized text. Zero comments emit zero bytes.
- `index declarations [--file <path> [<path>...]] [--kind <kind> [<kind>...]] [--name <name> [<name>...]]` emits selected indexed declarations as compact Markdown containing the declaration ID, logical source-root-relative file path, kind, names, and either the directly associated comment ID or the explicit absence value `none`. Several names are separated by a comma and a space. A declaration with no names uses `names:` with no value, which is not a synthetic identifier. `none` means the parser recorded no documentation comment on that declaration. It is not a defect. Zero declarations emit zero bytes.
- Discovery filters select already loaded facts without changing IDs, canonical order, or rendering. Each filter occurs at most once and consumes one or more consecutive values until the next filter or the end of arguments; unsupported options and missing values are usage errors before opening state. Values within one category use OR, categories use AND, and duplicates are deduplicated preserving first occurrence. `--file` accepts canonical non-empty logical relative slash-separated paths and matches only an exact path or descendants beneath `selector + "/"`; it does not resolve paths or inspect the filesystem. `--kind` compares the stored neutral kind exactly and case-sensitively without aliases; unknown kinds match nothing. `--name` matches any exact case-sensitive indexed name; nameless declarations do not match a supplied name filter. No matches succeed with zero output bytes. Filters do not change snapshot usability, currentness, persistence, or workspace selection.
- `index status` reports missing, current, stale, or corrupt without modifying the project. These states are successful inspections; operational failures to inspect the project are errors.
- `index show` resolves one or more snapshot-local comment or declaration IDs from a current index. A comment result contains the logical file, the physical comment lines, and bounded structural source context. It does not repeat normalized comment text in a separate section. A declaration result contains the logical file, the physical declaration lines, the kind, the names, the documentation comment ID or `none`, and bounded structural source context. It does not repeat documentation text as separate metadata. Source bytes are read to check currentness, then reread for context only after the snapshot is current. The context read rejects bytes that no longer match the fingerprint. Parsing for retrieval occurs only while building context for that current snapshot. Requested ID order and duplicates are preserved; a malformed or unknown ID fails without partial successful output.
- `index comments`, `index declarations`, `index status`, and `index show` never regenerate missing or stale indexes. `index comments`, `index declarations`, and `index show` fail for missing, corrupt, or stale indexes. Changing ignore configuration does not regenerate an index either.
- `ignore list`, `ignore enable`, and `ignore disable` use the resolved workspace control directory. `ignore list` creates nothing. `ignore presets` lists selectors without opening a project or workspace.
- `skill targets` and `skill show` list targets and emit the canonical skill, respectively, without opening a project. Project-local `skill install` and `skill uninstall` use ordinary root resolution, including explicit `--root`. Their `--global` option uses the current user's home without resolving a project and cannot be combined with `--root`. `--out-dir` has no effect on skill destinations and is not opened by skill commands.
- `version` prints the source-defined product version and linked commit and build date without opening a project. Product version is source-defined in `cmd/nodex/version.go`; `commit` and `buildDate` default to `unknown`, and release builds may override only those two metadata values.`commit` and `buildDate` default to `unknown`, and release builds may override only those two metadata values. Runtime code must not inspect version control or infer build identity from the working directory.

Well-formed global options are accepted without path inspection on state-independent commands (`version`, `ignore presets`, `skill targets`, and `skill show`). Global options support both separated and equals values, reject duplicates and missing values, and do not apply after the top-level command.
